## The one non-pass: T33 (minor, explained, hypothesis for the cause marked)
- Case: a student's ranked entry is overdue; the student opens the contest (`start_competition`). The function first sweeps (finalizes overdue entries), then correctly raises `already_submitted`. Because the function ENDS WITH AN ERROR, the sweep's changes inside that same call are rolled back, so that entry stays `in_progress` after the call. (Cause: standard Postgres behaviour, an error aborts the whole call; hypothesis confirmed by the test, not yet by reading Postgres logs.)
- Impact: low. The student still gets the right answer (`already_submitted`). The entry is finalized (and points awarded) by the next call that ends successfully and sweeps: `list_competitions` (every hub open), `competition_leaderboard` (closed phase), `submit_competition`. Points are only needed when the contest is closed, and the leaderboard sweeps before ranking (check T65 proves this).
- Not fixed, no migration written (owner order was tests only). Possible later fix if wanted: in `start_competition`, RETURN a JSON with an `error` field instead of raising after a sweep, or have the client call `list_competitions` first (it normally does). Decide in C3/C6.
